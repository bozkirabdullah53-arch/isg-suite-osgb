# İSG SUITE — yedi bulgu için uygulama ve sunucu kontrolü

Tarih: 2026-10-06. Bu belge NSL-2026-PRJ-106 V1.0 raporundaki **yedi**
bulguya aittir. Depodaki daha eski dokuz bulgulu rapor aynı numaraları farklı
başlıklarda kullanıyor; o raporun testleri bu bulguların kapanışı sayılamaz.
Parola, rapordaki oturum belirteçleri ve kişisel veriler bu belgeye aktarılmadı.

## Hedef ve mevcut yayın farkı

Okuma amaçlı kontrolde `www.isgsuite.com.tr`, `isgsuite.com.tr` ve
`mail.ideaisg.com.tr` aynı sunucu IP'sine çözüldü. Rapordaki uygulama adresi
`uygulama.ibysis.com` farklı bir sunucu IP'sine çözüldü. Bu deponun API'si
`/api/v1` kullanıyor; rapordaki `/api/hastalar`, `/api/egitim` ve `/api/dogrula`
uçları bu depoda bulunmuyor. Aynı uygulama veya aynı veri tabanı oldukları
varsayılmadı. Rapordaki uygulama için yetki ve kod sahibi eşleşmesi gerekir.

Canlı `.com.tr` adresindeki `/api/v1/live` 404, `/health` ise anonim 200 ve
servis adını içeren bir yanıt verdi. Güncel depo kodu boş 204 liveness yanıtı
ve sade sağlık yanıtı üretiyor. Ana HTML'de CSP, X-Frame-Options ve nosniff
başlıkları bulunmadı; HSTS bulunuyordu. Kodun ve etkili Plesk vhost ayarlarının
canlıda ayrı ayrı güncellenmesi gerekiyor.

Plesk IP'sinin 8443 portuna bu ortamdan yapılan iki okuma isteği 502 döndü.
Bu sonuç yama veya erişim kısıtlamasının uygulandığını kanıtlamaz; erişim yolu
ve sunucu üzerinden yeniden doğrulanmalıdır.

## Yapılan düzeltme

Nginx'te `/index.html` içindeki `add_header Cache-Control`, üst seviyedeki
**bütün** `add_header` güvenlik başlıklarının mirasını kaldırıyordu. Cache-Control
değeri artık HTTP seviyesindeki `map` ile hesaplanıp diğer başlıklarla aynı
`server` seviyesinde ekleniyor. Ana sayfa, doğrudan index ve SPA iç bağlantıları
aynı güvenlik başlıklarını ve no-store politikasını alıyor; statik dosyalar için
bu HTML önbellek politikası uygulanmıyor. CAPTCHA çerçevesi ve mikrofon izni
mevcut politikada korunuyor.

Gerçek Nginx HTTP testi düzeltmeden önce üç HTML rotasında başarısız oldu,
düzeltmeden sonra yedi senaryoda geçti. Test hem başarılı hem 404 yanıtlarını
ve başlıkların yinelenmemesini kontrol ediyor. Yeni backend senaryoları ve
Nginx testi mevcut CI'ya eklendi; bu belge uzaktaki CI'nın geçmiş olduğunu
iddia etmez. Yerel ve uzak test sonuçları ayrıca kaydedilmelidir.

## Sunucuda ilk adım: salt okunur durum kaydı

Yeni kontrol dosyasını inceleyip sunucuya kopyaladıktan sonra:

```bash
python3 /tmp/security_server_preflight.py --repo /opt/isg-suite-osgb --origin https://www.isgsuite.com.tr
```

Dosya bu depodaki `backend/scripts/security_server_preflight.py` dosyasıdır.
Uygulama paketlerine ihtiyaç duymaz; veri tabanına girmez, env/parola okumaz,
servis yeniden başlatmaz ve ayar değiştirmez. Git commit/temiz çalışma ağacı,
Plesk yama/eklenti sürümü, yalnız API erişim ayarının durumu ve dört anonim GET
kontrolünü JSON olarak verir. `FAIL` mevcut bir farkı, `CHECK` eksik kanıtı
gösterir; ağ hatası hiçbir zaman başarılı erişim kısıtlaması sayılmaz.

## Plesk düzeltmesi ve erişim sınırı

Sunucuda tam sürümü ve gizli REST API eklentisini doğrulayın:

```bash
sudo plesk version
sudo plesk bin extension --get-xml-info rest-api
```

Üreticinin CVE-2026-68492 duyurusuna göre Linux için düzeltme sınırları
Plesk **18.0.80.8 / 18.0.81.1**, REST API eklentisi **2.4.7**'dir. Yalnız
`18.0.81` yazması yeterli kanıt değildir. Etkilenen iki bileşenin birlikte
kurulu olması gerekir; güvenlik bakımında her ikisi güncel/yamalı tutulmalı.
Eklenti eskiyse üreticinin komutu:

```bash
sudo plesk bin extension --install rest-api
```

Plesk'in kendisini paneldeki Updates bölümünden üreticinin desteklediği güncel
yamalı sürüme güncelleyin. Öncesinde geri yüklenebilir sunucu/uygulama yedeği
ve çalışan yönetim erişimi doğrulanmış olmalıdır.

Plesk API kullanılmıyorsa mevcut `panel.ini` içindeki `[api]` bölümünü koruyarak
`enabled = off` ayarlayın. Kullanılıyorsa gerçek yönetim/otomasyon IP'lerini
`allowedIPs` alanına yazın. Dosyanın tamamını değiştirmeyin. Bu ayarların
anonim şemayı engellediği dışarıdan ayrıca test edilmelidir.

TCP **8443** erişimini sunucu veya sağlayıcı güvenlik duvarında yalnız gerekli
yönetim/VPN/otomasyon kaynaklarıyla sınırlandırın. Önce kendi yönetim yolunun
çalıştığını doğrulayın. Plesk'in “IP Access Restriction Management” özelliği
tek başına panelin tüm anonim kaynaklarını veya müşteri girişini engellemez;
ağ sınırı yerine geçmez. HTTPS 443, SSH yönetim yolu ve çalışan mail akışı
bu panel kısıtlamasına karıştırılmamalıdır.

## Uygulama yayını

Sunucudaki commit, çalışma ağacı, servis adı, üretim env doğrulaması ve gerçek
Nginx vhost yolu bulunmadan master'a körlemesine geçiş/yeniden başlatma yapmayın.
Mevcut servis başka bir paket veya dal kullanıyor olabilir. Güncel üretim kodu
PostgreSQL, Redis ve diğer güvenlik bağımlılıklarını zorunlu tutabilir; çalışan
ortamın bu koşulları karşıladığı önce doğrulanmalı.

Konteyner ön yüzü kullanılıyorsa `frontend/nginx.conf` imajda zaten kopyalanır;
test edilen sürümden ön yüzü yeniden oluşturup kontrollü yayınlayın. Plesk
doğrudan statik dosya sunuyorsa gerçek vhost'u buna göre uyarlayın. `map`
yalnız `http` seviyesinde geçerlidir: bu dosyanın tamamını panelin server
seviyesindeki Additional nginx directives alanına yapıştırmayın. Plesk'in
ürettiği dosyaları doğrudan değiştirip sonraki güncellemede kaybolacak bir
düzeltme bırakmayın. Tüm HTML/SPA location'larının güvenlik başlıklarını
aldığını, `nginx -t` ve dış HTTP kontrolüyle doğrulayın.

API'nin mevcut güvenlik iyileştirmelerini doğru sunucuya yayınladıktan sonra
`/api/v1/live` anonim, boş **204** olmalı. İzleme/proxy sağlık kontrolünü bu
uçta doğrulayın; ardından gerçek üretim servisinin env'inde
`HEALTH_AUTH_REQUIRED=true` etkinleştirilebilir. `/health` anonim 401, normal
kullanıcıyla 403 ve global yöneticiyle 200 olmalı. Başlıkları backend ve Plesk
katmanlarında çakışan/yinelenen CSP kuralları bırakmadan düzenleyin; Turnstile
ve olağan giriş/MFA akışını test edin. VITE Turnstile site key gizli server key
yerine geçmez; gerçek anahtarlar olmadıkça CAPTCHA etkinleştirilmemeli.

Sağlık kayıtlarının arşivlenmesi fiziksel silme değildir. Bu kod düzeltmesi
silinen kaydı normal erişimden çıkarır ve denetim geçmişini tutar; yasal saklama
koşulları incelenmeden veri tabanında toplu veya kalıcı silme yapılmamalıdır.

Mail ekranındaki TLS çıktısı bu yedi bulgunun tamamının geçtiğini göstermez.
Önceki mail bulguları da kapatılacaksa hostname/sertifika doğrulaması, başarılı
TLS anlaşması, gerçek şifreli gönderim/alım ve DKIM/DMARC kanıtı ayrı gerekir.

## Yerel doğrulama sonucu

Seçili **165 farklı backend/güvenlik testi**, **407 ön yüz testi** (67 dosya,
Node 20.20.2, en çok iki işçi) ve gerçek Nginx 1.28.0 üzerinde **7 HTTP testi**
geçti. İlk 51 kontrol, ek 103 kontrol ve son 11 kontrolün toplamı 165'tir;
son koşu dokuz yeni senaryoyu ve önceki koşuda atlanan iki Redis entegrasyonunu
içerir. Üç Redis senaryosu gerçek Redis 7.4.0 üzerinde çalıştı. Test Redis'i
yalnız localhost üzerinde başlatıldı ve koşu sonunda durduruldu.

Node 20.20.2 ile üretim derlemesi geçti; lint 0 hata, 57 mevcut uyarı verdi.
Tam backend paketi, PostgreSQL CI ve tarayıcı E2E çalıştırılmadı. Staging'e özgü
tarayıcı kapısı bu yerel build'de atlandı. Kodun canlı sunucuya uygulandığı veya
harici sızma testinin kabul edildiği iddia edilmemektedir.
